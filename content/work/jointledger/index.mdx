## One-minute summary

JointLedger is my fork of ezBookkeeping — an open-source, self-hosted personal finance app — extended with a Book/BookMember data model so a household's accounts, categories, and tags can eventually be shared and permission-checked, not just owned by one person. A personal book is created automatically for every user, existing users get backfilled onto one by an idempotent migration command, and a shared book supports owner/editor/viewer roles enforced on every request. This work lives on an unmerged feature branch on top of ezBookkeeping's own codebase, not yet on the fork's default branch: there is no book-selector or invitation interface yet, transactions themselves aren't book-scoped in reads yet, and invitations exist only as an unused database table. Every other claim in this write-up is a claim about this specific branch's code, not about a finished product.

## Why it exists

ezBookkeeping is genuinely well-built for one person's own finances, but a household's money doesn't stay that clean — some accounts are individually owned, some are genuinely shared, and "give my partner my login" is not a permission model. JointLedger's real subject is the underlying question of what has to change in a single-owner bookkeeping app's data model to let more than one person see and edit the same set of accounts safely, without touching the accounting logic ezBookkeeping already gets right.

## Constraints

- **Unmerged feature branch**: the entire Book/BookMember implementation exists on `feature/shared-family-book`, not on this fork's default `main` branch — a repository visitor browsing the default branch today would not see any of it.
- **Solo-built in a single working session**: all four feature commits building the Book/BookMember system were made on 2026-07-07, within about 7.5 hours (16:08–23:48) — verified directly from commit timestamps; the initial fork setup itself was four days earlier.
- **No frontend integration yet**: zero references to a book id exist anywhere in the Vue frontend — every screen a user actually sees is still ezBookkeeping's own, unmodified interface.
- **Transactions aren't book-scoped in reads yet**: `bookId` is set when a transaction is created, but every transaction query still filters by the classic single-owner `uid` — the shared-visibility promise doesn't reach the ledger's own core entity yet.

## Reflection

What holds up under direct code reading: the permission model is real and tested — `CheckBookPermission` genuinely checks a caller's own membership row and role before any book-scoped query runs, a dedicated test creates a shared book with an owner, an editor, and a viewer and confirms each role's actual access (and a non-member's rejection), and the personal-book backfill is provably idempotent — re-running it doesn't create a second book or reprocess already-scoped data. Accounts, categories, and tags are genuinely, not superficially, book-scoped: every read and write for those three entities resolves a book, checks the caller's permission, and queries by `bookId`.

What's honestly weaker than "shared finance system" implies: there's no book-selector or invitation interface anywhere in the frontend, so all of this is currently reachable only by calling the API directly. Membership today is direct add-by-owner (by user id, username, or email), not an accept/decline invitation — `BookInvitation` exists as a database table and a set of status values, but no code anywhere creates, sends, or accepts one. And transactions — the entity the whole idea of a "shared ledger" is really about — aren't book-scoped in any query yet, so two members of the same shared book still can't actually see each other's transactions through this system. One more honestly-disclosable finding from the audit: the member-add endpoint resolves a target user by email or username before confirming the caller has permission to manage the book in question, which could let an authenticated user probe whether an email address belongs to a registered account regardless of their own access to that book — a general hardening gap, not something this write-up demonstrates how to exploit.
