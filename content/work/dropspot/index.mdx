    context: "A claim has to check the claim window, check remaining stock, and check the caller's waitlist position, then write three tables — without letting two simultaneous claims both succeed against stock that only has room for one."
    choice: "Every claim runs inside a single PostgreSQL transaction that takes a `SELECT ...     tradeoff: "Every claim request briefly holds a row lock on the drop being claimed, so claims against the same drop cannot be processed in true parallel by the database — an acceptable cost for a claim window's write volume, but not a design for extremely high-throughput contention on a single row."

    context: "The waitlist needed an ordering rule that rewards genuine early/loyal signups without being a single fixed formula every deployment (and every user who reads the source) can predict and game identically."
    choice: "A SHA-256 hash of the git remote URL, the repository's first commit timestamp, and a build-time value produces a 12-character seed; three coefficients (ranges 7–11, 13–19, 3–5) are derived from that seed and used in the score formula `1000 + (signup_latency_ms % A) + (account_age_days % B) − (rapid_actions % C)`, floored at zero."
    alternatives:
      [
        "A single fixed formula with hardcoded constants, identical across every deployment of the codebase",

    context: "The database needed a repeatable way to reach a known schema for development, testing, and CI — DropSpot has no production deployment or existing user data that a schema change would ever need to preserve."
    choice: "One migration script drops and recreates all four tables (with their foreign keys, `CHECK` constraints, and indexes) in a single transaction; the same script runs before the backend's own test suite in CI."

    tradeoff: "This script cannot be run safely against a database with real data to keep — it is a reset, not an upgrade path — which is a reasonable trade for a project with no live deployment, but would need to become a real versioned migration system before one existed."

## One-minute summary

DropSpot is a fair-claim and waitlist system for limited-stock product drops, built as a self-directed technical case study rather than a deployed product. A visitor can browse drops without an account; joining a waitlist and claiming a drop require signing up. When a drop's claim window opens, eligibility is decided by a priority score — computed from account age, a (largely inert, see Reflection) signup-latency term, and a rapid-action penalty — and the claim itself runs inside a PostgreSQL transaction that row-locks the relevant records before checking the claim window and remaining stock, so two simultaneous claims against the last unit of stock cannot both succeed. An admin role can create, edit, and delete drops through a separate panel. There is no live deployment, no real users, and no usage data — every claim in this write-up is a claim about the code, not about production behavior.

## Why it exists

DropSpot was built to work through a specific, concrete distributed-systems problem in a small enough scope to actually finish: what does "fair" mean when more people want a limited-stock item than there is stock, and how do you stop a race between two simultaneous claims from ever giving the same unit to two different people? Rather than a generic CRUD app, the project's real subject is the claim path itself — the transaction boundaries, the row locks, and the ordering rule that decides who is even eligible to claim once a window opens.

## Constraints

- **No production deployment**: DropSpot has never run against real traffic or real users; every technical claim here is a claim about the code and its tests, not about observed production behavior.
- **Solo-built, over two days**: the entire codebase — schema, backend, frontend, and both test suites — was written by one person, verified against the repository's own commit history (2025-11-06 to 2025-11-07, 31 commits), not iterated on since.
- **PostgreSQL-specific concurrency strategy**: the claim path's safety guarantee depends on `SELECT ... FOR UPDATE` row locking, a PostgreSQL-specific mechanism, not a database-agnostic one.

## Reflection

What holds up under direct code reading: the claim transaction genuinely does what the README says it does — row locks taken before the stock and claim-window checks, four writes committed together, and idempotent responses (not errors) when a user joins or claims twice. The priority-score seed is real and unit-tested, deriving different coefficients per deployment rather than shipping one fixed, guessable formula.

What's honestly weaker than the README's own framing suggests: the `signup_latency_ms` term in the priority formula is computed from two `Date.now()` calls made back to back on the same line in the frontend, so in practice it contributes close to nothing — account age and the rapid-action penalty do the real ordering work, not signup speed. The repository also contains a GitHub Actions workflow file for CI (a real Postgres service container, a backend test job, a frontend build job) — but it's committed at `github/workflows/ci.yml` instead of `.github/workflows/ci.yml`, so GitHub Actions never actually recognized or ran it; the pipeline was authored but never went live. No test in the repository exercises genuinely concurrent, simultaneous requests against the same drop — the locking mechanism is verified by reading the transaction code directly, not by a passing concurrency test. And no accessibility-specific work (landmark roles, `aria-*` attributes) exists anywhere in the frontend source. None of this changes what the claim transaction itself verifiably does — it's exactly the kind of gap a from-scratch, timeboxed build honestly has.
