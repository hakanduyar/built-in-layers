## One-minute summary

Kıvılcım is a personal, local-first PWA for planning, focus, and growth, organized around five areas: Today, Plan, Mind, Focus, and Progress. Primary application data lives in IndexedDB, while a small amount of device-local configuration, including the optional Gemini key, is stored in localStorage. There is no backend or account system, and the core planning, focus, and review workflows continue to work offline after the app has been installed. The core loop is simple: capture what's on your mind, plan what matters, run a focus session against it, and close the day with a short review. An optional AI layer (a user-supplied Gemini key) can help draft tasks from notes and summarize a week, but the app is fully usable without it. It's under active, ongoing development — the interface is currently Turkish-language only, and a handful of areas planned in the schema (habit-specific tracking, weekly review) don't have a screen yet.

## Why it exists

Most task managers assume the hard part is remembering what to do. In practice, the harder part is deciding what to start and actually starting it — decision fatigue, not memory, is usually the real friction. Kıvılcım is built around that problem specifically: a small, opinionated set of screens (not an open-ended list app), a focus timer that turns "start something" into a concrete, timed commitment, and a lightweight XP/level layer that rewards the act of finishing a session or a task, not just planning one. It isn't a generic to-do app with extra features bolted on — the five-area structure and the focus-first loop are the actual product idea, not decoration around a task list.

## Constraints

- **Local-first, single-user**: everything lives in IndexedDB on one device; there's no account system and no server-side code to audit or maintain.
- **Mobile-first PWA**: designed and used as an installable home-screen app; desktop is not the primary target.
- **AI is optional, never required**: no core flow depends on an external API call or an API key being present.
- **No automatic sync**: moving data between devices is a manual, user-initiated JSON export/import — an explicit trade-off of the local-first choice, not an oversight.
- **Turkish-language UI today**: every visible string in the current build is in Turkish. This case study is written in English, but the product itself is not yet localized.
- **Personal-use scope**: built for one person's own daily use, not designed or hardened for multi-tenant or public deployment.

## Evolution

The project started with the basics: a Vite/React/TypeScript scaffold, Tailwind, PWA setup, and a dark mobile shell, followed by the Dexie database and its first table set. From there it grew screen by screen — Today (with a rule-based coaching note and the day's tasks), Plan (task creation, editing, completion, filtering, promoting a task to the day's focus), Focus (the timer itself, with 5/15/25/45-minute presets and XP on completion), and a JSON backup/restore system early enough to make iteration safe.

Mind (capture and a saved-links vault) and the optional AI layer (Gemini-backed task drafting and coaching notes, fully gated behind a user-supplied key) followed, then Progress (XP, levels, per-area stats). After that initial build-out, development continued well past the original plan: Routines (recurring tasks generated day-by-day, replacing an earlier idea of extending the unused Habits tables), a general Plans/Important Dates system for goals and deadlines with linked tasks and progress tracking, four calendar views (day/week/month/year) unifying tasks, routines, and plans on one timeline, a full pass hardening the XP model against double-awarding, and a final UX/mobile-stability polish pass.

## Reflection

What's held up well: the focus-timer state machine, the XP model's award-once guarding, and eight versioned schema migrations designed to preserve existing records as tables and indexes changed — the kind of thing that's easy to get wrong quietly and hard to fix retroactively. The local-first, optional-AI stance has also stayed intact throughout, rather than eroding as features were added.

What's honestly incomplete: `habits`/`habitLogs` exist in the schema and in JSON backups but have no screen — recurring commitments are handled by Routines instead (see the decision above), which works, but leaves that original table as quiet debt. The same is true of `weeklyReviews` — reserved in the schema, never wired to a screen. Progress is currently plain stat cards and bars; a "Recharts graphs for better statistics" item is explicitly still on the project's own to-do list, not yet built. And the product has no English UI yet, which matters for anyone outside its current single user trying to actually run it.

What's next, honestly stated rather than promised: real product screenshots for this case study, and — separately from this write-up — the schema cleanup or removal for the unused habit/weekly-review tables, whichever the actual usage pattern ends up justifying.
